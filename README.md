# Recenter

**Return to what matters.**

Capture the idea of returning to your values, intentions, and commitments throughout the day.

An Electron desktop application with React, TypeScript, and Vite.
The main process, secure preload bridge, and React renderer are built together
with electron-vite. Electron is pinned to 44.5.1.

## Run locally

Use Node.js 24 LTS to run the full test suite. Open PowerShell in the project
directory (the folder containing `package.json`), then run:

```powershell
npm.cmd ci
npm.cmd run dev
```

The development command opens a native Electron window. The local Vite server
provides live updates inside that window; you do not need to open a browser.
It also watches main/preload changes: main changes restart Electron and preload
changes reload the renderer with the rebuilt bridge.
Close the window and press Ctrl+C in the terminal to stop development.
`npm.cmd` avoids PowerShell script execution policy restrictions. In Command
Prompt or other shells you can use `npm` instead.

## Persistence and migration

The main process owns the reminder list and notification receipts in
`personal-reminders.json` under Electron's `app.getPath('userData')` (normally
`%APPDATA%\reminders` on Windows). Writes use a flushed temporary file followed by
an atomic rename. Failed writes leave the UI list unchanged. An unreadable file
is reported without replacing it with an empty list.

The old `localStorage` key `reminders.personal.v1` is preserved. On first load
from each renderer origin, the app validates and imports its personal reminders,
retains an exact `personal-reminders.json.legacy-*.json` backup, and records the
import in the canonical file. Importing that origin again cannot replay stale
edits. Existing canonical records win ID conflicts; the original conflicting data
remains in its backup. Deleted IDs are retained so another old origin cannot
resurrect them. Malformed/unavailable legacy data blocks that origin's import and
is never silently discarded. Defaults are hard-coded UI samples and never imported.

Development (port 5173) and compiled mode now share the canonical file in the same
app profile. To import old reminders from both modes, open each mode once, one at
a time. Other historical localhost ports must likewise be opened once at their
original origin. No attempt is made to read Chromium's internal storage files.
Do not clear the old storage before importing it. Clearing browser storage after
migration does not erase the main-process reminder list.

The reminder-list preload bridge exposes only initialize, save, remove and status methods.
A separate restricted popup bridge exposes get, begin, pulse and cancel. The main
process validates all payloads, the sending window, main frame and renderer URL.
No generic IPC, filesystem access or Node.js APIs are exposed. Context isolation,
renderer sandboxing and disabled Node integration are unchanged.

## Scheduling behavior

- The main process checks personal reminders every second and again on resume from
  sleep. Minimizing or reloading the window does not stop it.
- Does not repeat fires once. Daily and Weekly use local calendar dates and the
  saved time (Weekly follows the starting date's weekday).
- On startup/resume, a one-time overdue reminder fires once. Missed repeats are
  coalesced into one alert for the latest due occurrence, rather than a backlog.
- A durable occurrence receipt is committed before calling Electron's Notification
  API. The same occurrence is not sent twice after reload, resume or restart.
  Native notification delivery is at-most-once: a crash after the receipt but before OS display,
  or an OS delivery failure, can miss that alert; it will not be retried. Exactly
  once visible delivery cannot be guaranteed by Electron and the OS.
- A title/note edit does not replay an occurrence. Changing date, time or repeat
  updates the schedule, but an already handled reminder/date/time stays handled.
  Deleting cancels future occurrences. No sample defaults
  are scheduled.
- Spring DST gaps move delivery to the normalized local time (e.g. 02:30 becomes
  03:30). The repeated hour in autumn still has one occurrence identity. Clock
  rollback does not replay occurrences already covered by a receipt.
- A single-instance lock and one scheduler interval prevent multiple scheduler
  processes. Shutdown stops the interval; there is no auto-start or background
  service. On Windows, closing the window quits the app. Closed apps cannot alert;
  the next launch catches up. On macOS, the app can remain running without windows.
- Clicking an alert restores/shows/focuses the existing window, or creates one if
  the app is running without a window. Windows notification activation is also
  handled centrally.

## Windows notification check

1. Run `npm.cmd run dev` (or `npm.cmd run build` then `npm.cmd start`).
2. Add a personal reminder for today's date, two minutes in the future, with
   Does not repeat. Save it and minimize the app.
3. At the saved time, look for its native Windows notification. Click it to bring
   the app forward. Wait a minute, then restart: the same occurrence must not alert
   again.
4. For catch-up, add another future reminder and quit before it is due. Reopen
   after its time: it should alert once, and not repeat on a second restart.
5. Try Daily and Weekly reminders anchored in the past. Each sends at most one
   catch-up; subsequent deliveries follow its daily/weekly schedule. Editing to a
   future minute reschedules it; deleting before that minute cancels it.
6. Verify the four default cards never generate notifications.

If a banner does not appear, open Windows Settings > System > Notifications,
allow notifications for Electron/Recenter, and turn off Do not disturb while
checking. The footer reports unsupported notifications or explicit delivery errors
and includes details in its tooltip. Support detection alone cannot establish
whether Windows has muted banners or suppressed a specific alert.

In development the AppUserModelID is the Electron executable path. If Windows has
not registered it, pin `node_modules\electron\dist\electron.exe` to Start as
described in [Electron's notification guide](https://www.electronjs.org/docs/latest/tutorial/notifications#notifications-in-development).
Packaged distributions will need a matching Start Menu shortcut/installer identity
(`com.reminders.desktop`). This internal identity is retained for upgrade and
notification compatibility; the displayed product name is Recenter.
Windows does not use a web-style notification permission prompt. On macOS,
Electron's native backend requests authorization; allow it in the OS prompt/settings.
A signed application is needed for reliable macOS notification support. Linux
requires a desktop notification service. Unsupported systems and native failed
callbacks are handled without crashing or re-firing a claimed occurrence.

## Verification

- `npm.cmd run typecheck`: Electron, shared types, bridge and React checks.
- `npm.cmd test`: validation, legacy storage, atomic store/migration, scheduling,
  daily/weekly repeats, DST, duplicate prevention, edits/deletes and restart tests.
- `npm.cmd run test:desktop`: production build, real Electron create/edit/delete,
  persistence across restarts, secure bridge, storage recovery and duplicate
  prevention using disposable profiles. By default the tests hide app windows.
  Notification creation/click/failure checks and visible popup/overlay tests are
  **opt-in**, using `REMINDERS_INTERACTIVE_TESTS=1` as described below. Native
  notification display is stubbed in both modes to avoid sending real OS toasts.
- `npm.cmd run build`: TypeScript checks and production build.

No lint tool/script is configured. No database, Supabase, website blocking or focus
mode is used. The notification engine is independent of the renderer and does not
change the existing two-panel design.

## Loading errors and restarting after an update

If a renderer update expects a new preload bridge while an old Electron process
is still running, the previous UI showed a generic storage error and disabled
New Reminder. A window refresh cannot replace already-loaded main-process code.
The development command now uses `electron-vite dev --watch` to keep these parts
in sync, but an already-running older dev command needs one full restart:

1. Close the Recenter window using its X button (do not just minimize it).
2. In the terminal running the old dev command, press Ctrl+C. If Windows asks
   to terminate the batch job, answer Y.
3. From the project directory, run:

   ```powershell
   npm.cmd run dev
   ```

Wait for the new Electron window. Verify your saved reminders appear, then use
New Reminder to save a test item, edit it, restart and confirm it persists.
Delete that item and restart once more to confirm deletion persists. For compiled
mode, use `npm.cmd run build` followed by `npm.cmd start` after closing the old app.

Loading errors now include the underlying bridge/IPC/file error, which is also
logged in the renderer console. Retry loading actually calls initialize again;
if the main process could not open the store, it retries that open as well.
New Reminder can still open the form during a load failure, but saving is blocked
until the existing list loads, preventing accidental replacement. Retry is also
available inside the form. A missing/outdated preload specifically asks for a full
restart; Retry cannot inject a preload into an already-running old host.

No recovery action deletes or resets storage. Existing localStorage is read only
for the validated import and kept intact. The regression suite reproduces an old
host without a bridge, failed load/retry, recovery of a failed main-process store,
legacy import with exact backup preservation, and persistence after recovery.

## Duplicate occurrence prevention

Occurrence delivery is deduplicated by personal reminder ID and its actual local
scheduled date/time. The existing signature-bearing keys remain readable and are
not reset. Repeat/anchor edits cannot queue the same occurrence twice. A handled
history entry takes precedence over a missing or newer scheduling receipt.

The store returns only unique, unhandled popups to the window controller. Old
duplicate queue entries are not shown again. Successfully holding dismiss commits
the handled timestamp and removes all copies of that occurrence atomically, while
leaving other reminders queued. A read/restart does not rewrite or reset data.
Daily and Weekly reminders remain eligible on their next actual scheduled date.
The scheduler invokes delivery only for a newly accepted claim, and installs its
single timer before its initial tick so reentrant startup cannot add another timer.

`npm.cmd run test:desktop` now runs without showing test reminder windows. Visible
popup/black-overlay scenarios are opt-in, to avoid automated test reminders being
mistaken for repeatedly triggered personal reminders. To deliberately run the
interactive desktop suite in PowerShell:

```powershell
$env:REMINDERS_INTERACTIVE_TESTS = '1'
try {
  npm.cmd run test:desktop
} finally {
  Remove-Item Env:REMINDERS_INTERACTIVE_TESTS -ErrorAction SilentlyContinue
}
```

Those interactive tests open real reminder windows and require an undisturbed
desktop. On Windows, keep the real cursor over the popup's hold button during
the synthetic hold checks; mouse movement or capture loss correctly cancels a
hold and can fail an automated run. The tests report pointer/focus events if a
full hold fails. Normal unit checks cover the five-second guard and recurrence without
displaying popups. The non-interactive Electron suite checks restart behavior
against a legacy queue containing already-handled duplicate occurrences, and
asserts that no popup, black overlay or native notification is created and that
the original fixture file is unchanged.

## Reminder popups

Each newly due personal occurrence also opens a dedicated centered, always-on-top
popup, independent of the main window and OS notification permission. The existing
native notification remains enabled when supported. The main page is unchanged.

The popup shows the title, optional note and a large **Hold for 5 seconds to
dismiss** button. Mouse and touch pointers are supported. Releasing early,
leaving the button, cancelling a pointer or switching focus resets progress.
Pointer capture plus coordinate checks handle touch movement outside the button.
The main process verifies focus, a monotonic 5000ms duration, and heartbeats no
more than 500ms apart. The renderer cannot submit an arbitrary completion time
or directly acknowledge an occurrence. A stalled renderer must start over.

The existing JSON file now also contains `pending` occurrences and `handled`
acknowledgement timestamps. Existing files without these optional fields load
without losing reminders or previous notification receipts. A due receipt and
its queued popup are committed atomically. One popup is shown at a time; other
occurrences remain on disk. Dismissal commits the acknowledgement before closing
the window and advancing the queue. Failed writes keep the popup open for retry.
Already-handled occurrences do not reopen. Unfinished popups resume after app
restart or a popup renderer crash. Old notifications delivered before this feature
are not retroactively turned into popups.

Deleting a reminder also cancels its queued occurrences. Editing a reminder does
not change the snapshot of an occurrence already due; its new schedule applies
to subsequent triggers. Missed repetitions while the app was closed still use
the existing latest-occurrence catch-up policy. Already queued occurrences are
retained individually, even when a later daily/weekly occurrence becomes due.

Popup IPC accepts only the dedicated popup window, its main frame, and its exact
renderer URL. The normal app window cannot begin or finish a popup hold. The
popup cannot invoke the main window's reminder editing API. Both windows retain
sandboxing, context isolation and disabled Node integration. The title bar area
can be dragged; normal popup closing (including Alt+F4) does not acknowledge it.
Closing the main app on Windows still quits the app; unfinished items stay queued.

### Manual Windows popup check

1. Fully close the old app and stop its dev terminal with Ctrl+C, then run from
   the project directory:

   ```powershell
   npm.cmd run dev
   ```

2. Add a personal reminder for one or two minutes ahead. Minimize the main window.
   At the saved time, the popup should appear above normal windows with its title.
3. Hold the button for two seconds and release. The popup stays and progress
   resets. Repeat while moving outside the button, then while switching apps:
   both attempts must reset.
4. Hold continuously for five seconds. Progress fills, the popup closes, and that
   occurrence does not reappear after restarting.
5. Create two reminders for the same time. Dismissing the first reveals the second.
   Quit the main app before dismissing the second; restart and finish it. Only the
   unfinished popup should return.
6. Test Daily and Weekly reminders with a past start date for one catch-up, then
   check the next daily/weekly occurrence. Default sample cards never open popups.
7. On a touchscreen, hold with one finger and repeat the early-release and
   move-outside tests. Automated desktop checks use real mouse input; touch event
   handlers are shared but physical touchscreen testing is manual.

Additional files: `main/reminderPopup.ts` controls the popup and restricted IPC;
`main/holdGuard.ts` validates holds; `shared/popup.ts` defines payloads;
`renderer/popup.html`, `renderer/src/popup.tsx` and `popup.css` form its separate
React entry. The Vite config builds both windows. `tests/popup.test.mjs` checks
hold timing, queues, recurrence and persistence; `tests/popup-desktop.cjs` checks
actual pointer input, focus loss, secure IPC, queuing and restarts. Unit checks
run with `npm.cmd test`; the visible desktop scenarios run only when
`REMINDERS_INTERACTIVE_TESTS=1` is set for `npm.cmd run test:desktop`.

## Black screen behind reminder popups

The existing reminder popup and five-second hold behavior are unchanged. When
its window is ready, a separate solid-black Electron window covers each connected
monitor's full display bounds (including taskbar space), and the popup is raised
above those windows. Overlay windows cannot take keyboard focus, expose no
preload/IPC APIs, and retain sandboxing, context isolation and disabled Node access.
No Windows display settings or other applications are changed.

There is one overlay per monitor for the active occurrence. Repeated scheduler
checks reuse those windows. Monitor add/remove, resolution and scaling changes
refresh the bounds. Early release leaves the overlays in place. Existing popup
completion/closure, renderer failure and app shutdown paths remove all overlays
and screen listeners. The existing pending-popup recovery may recreate both popup
and overlays after a failure; abandoned black windows are not left behind.

Files changed for this addition: `src/main/blackOverlay.ts` manages monitor coverage
and cleanup, `src/main/reminderPopup.ts` attaches that lifecycle to the existing
popup, and the desktop/unit test files verify overlay behavior. No popup renderer,
hold validation, scheduler, reminder storage or main-page design was changed.

To check on Windows, close the old app, stop its dev terminal with Ctrl+C, then
run `npm.cmd run dev` from the project directory. Schedule a reminder a minute
or two ahead and minimize the main window. All connected screens should become
solid black, with the existing popup above the black cover. Release the hold early:
both should remain. Complete the full hold: normal screens should return, unless
another queued reminder is immediately shown. Check again with a second monitor,
and with a monitor connected/disconnected while a popup is active. Closing the
main app must remove the black cover. Restarting may restore an unfinished popup
with its cover, following the existing queue behavior.
